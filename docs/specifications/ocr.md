# OCR（本戦スクショ）

## 2026-09-01 追加事項

- OCR後の新規出走登録で、衣装選択、トレーナーアイコン、意気込みコメント（40文字まで）を登録できる。
- OCRはトレーナー名を `trainerName` として読み取り、新規登録の出走者欄へ渡す。名前の近くにある丸囲みの `i` はゲーム内詳細ボタンとして除外する。
- 衣装は、OCRで確定したウマ娘に属する1〜3件だけで照合する。全角半角・空白・角括弧を無視した完全一致を優先し、不一致時は最大2〜3文字の編集距離を許容する。最有力候補が同率の場合は自動選択せず、登録前に候補から目視で確認する。
- 登録済みウマ娘の詳細確認中は、ヒーローの「出走登録」を選ぶと新規登録画面へ戻れる。
- 登録済みウマ娘の詳細確認では、不採用スキルの横から、その頭の候補だけを戦略例外モーダルへ渡して追加できる。候補専用モーダルで追加を確定すると、評価点差分を確認して一括反映し、候補モーダルは閉じる。
- 出走登録・開催設定の完了通知は右上トーストで表示し、表示後にURLの `msg` / `err` を除去するため再読み込みでは再表示しない。

## 育成ウマ娘・衣装ID（2026-08-29）

出走登録時、OCR は `name` に加えて画面上の角括弧内の `costumeName` を読む。Worker は `src/data/uma-dress-catalog.json`（DMM版 `master.mdb` から抽出）でウマ娘名・衣装名を一意にファジー照合し、確定した場合だけ `horses.chara_id` と `horses.dress_id` へ保存する。

- 照合不能・候補が一意でない・`0010` 画像未収録の場合は ID を保存せず、画像はなしとして扱う。名前から別衣装を推測しない。
- 共通関数 `resolvePetitImageUrl(charaId, dressId)` は、収録済みのときだけ `/images/umamusume/petit/petit_{chara_id}_{dress_id}_0010.png` を返し、それ以外は `null` を返す。
- 既存出走データのIDは `null` のままで互換性を保つ。編集でも保存済みIDを保持する。

## 方針

入力は **アプリ外で結合済みの完成スクショ1枚**。ゲーム内キャプチャや画像結合は当アプリではやらない。メンバー提出は umamusume-receipt-capture および有志のレシート因子メーカーを使う想定。

流れ: **完成画像を選ぶ → OCR → 登録**。読取に成功した画像が、その頭のスクショとして保存される。読めなかった頭は直置き（スクショなし）と混在できる。Gemini が1頭分を配列 `[ { ... } ]` で返した場合は先頭オブジェクトを使う（ルートが配列だと `name` / `skills` が取れず確認画面が空になる）。配列応答の読取〜登録は実機確認OK（2026-09-05）。

ベースはデスクトップアプリ **umamusume-skill-emulator** の OCR 遺産（Gemini で詳細ステータス画面を JSON 化）。当アプリ向けに切り出すものは読取とテキスト化まで。シミュレーション・オートキャプチャ・結合は持ち込まない。

遺産の参照先（ローカル）: `Documents/google antigravity/umamusume-skill-emulator`（特に `desktop-app/app/lib/geminiOcr.ts`・`fuzzyMatcher.ts`）。

## 実行場所（B）

**Gemini 呼び出し**は管理者のブラウザが直接行う。Workers に API キーは置かない・送らない。

- キーは操作する人の端末（管理画面のこのブラウザ）に置く。リポジトリ・`wrangler` の vars・サーバ秘密には置かない
- 請求と無料枠はキーの Google アカウント。無料枠で金銭ゼロに寄せる。課金アカウントは紐づけない
- モデルは遺産と同じ `gemini-3.1-flash-lite`（画像読取。画像生成モデルではない）
- 出走登録の操作者は当面作者。Neko長明さんが触るときは **本人のキー** か、OCR なしの直置き。作者のキーは渡さない

**保存用の画像**は Gemini とは別経路。本体は R2、D1 には参照だけ。キーは乗せず、画像ファイルだけ Worker へ送る。表示は出走タブ（管理のみ。`GET /admin/shot/{horseId}`）。

### R2画像の保持・削除

- `published` を含む正式開催のスクショとトレーナーアイコンは、出走・投票・払戻データとともに保持する。
- `setup` 中に画像を置換したり、馬・開催を削除した場合だけ、不要になった旧画像を削除対象にする。
- 削除直後は削除予定として保留する。未参照のまま次の対象操作が成功するとR2から削除する。
- R2削除が一時的に失敗しても、削除予定を残して後続操作で再試行する。管理者がR2を手作業で削除する必要はない。

## 登録名

出走は **ウマ娘名** と **出走者** を分ける。OCR のキャラ名はウマ娘名へ流す。出走者は手入力。

メンバー画面は **列を分ける**（仮）。ウマ娘名と出走者を別セルにする。

## 管理画面

OCR とスクショ保存は **`/admin/register`**。出走タブ（`/admin/horses`）でスクショを見る。管理ログインが要る。

メンバー画面には評価点も読取ログも出さない。**スクショは今はメンバーに出さない**（後ほど実装予定）。

1 頭ずつ完成画像を選ぶ → 読取 → ウマ娘名・ステ・適正・スキルをテキストで見せて直せる → ウマ娘名へ OCR を流し、出走者と評価点は手入力して登録。**読取成功時は、読取に使った画像が必ず保存される**（別の画像選択・保存枠は置かない）。キー未設定・失敗・未読取の頭は今どおり直置き（スクショなし）。一括貼り付けは置かない。

### 出走登録の表示 UI

- 複合回復の通常金スキルは有効スキル欄に残し、対象チップは `準金 +1` と表示する。金相当スキル数には含めず、内訳は「有効 / 金 / 準金」。回復量は従来どおり回復欄と実効スタミナに反映する

- **モード**: `idle`（ドロップ）→ `read`（読取確認）／ `manual`（スクショなし直置き）。`idle` から「スクショなしで直置きする」でも `manual` へ
- **読取確認の材料**（上から）: 有効スキル → スタミナ消費 → 戦略例外 → 緑 → 回復 → 不採用 → OCR落ち。回復は純回復をすべて、複合回復は有効スキルだけ表示する。純回復は不採用欄へ重ねて出さない。自己消費も有効スキルだけ表示する。ステ5値・適性はチップ。脚質別スタミナ目標値は開催設定で入力する
- **評価点行**: 自動算出が既定のときは「評価点 · 自動算出」ラベルだけ見せ、**評価点を直置き** pill（脚質 seg と同系）で手入力へ切替。pill ON で数値欄表示。`manual` モードは常に数値欄＋ pill
- **編集**（`/admin/register?edit=`）: 直置き pill は新規と同型。不採用からの「例外に追加…」は新規読取確認だけ（編集では出さない）
- **ヒーロー右**: 運営の事前評価・ウマ番編集・戦略例外件数・Gemini キー操作（キーはブラウザ local のみ）。運営の事前評価は全頭に対して順位とメモを任意入力でき、順位の重複は不可

**出走脚質**は頭ごとに人が選ぶ（逃／先／差／追）。OCR の脚質適性に S が1つだけあれば、その脚質を初期選択にする。S が0・複数・未読取なら未選択。変更可。緑条件と U-tools 有効リストに使う。開催条件の手打ちは [score.md](score.md)。

スキル名はカタログへファジー照合して **id 化する**（`skillFuzzy.ts`。遺産 `fuzzyMatcher` 相当。緑×落としはしない）。カタログは同名の unique / inherit / special を id 単位で保持。先頭スキルは固有、以降は継承進化→通常継承の順で解決。OCR 一文字ずれは編集距離≤1と既知エイリアスで拾う。`千.万.`（4文字）でカタログに無い成語寄せは千鍛万錬へ（カタログ唯一のため）。**エイリアスの人間向け一覧は [ocr-aliases.md](ocr-aliases.md)**（コードと揃える）。ためらい4種もカタログに含む。材料は `horses.score_input` に保存。評価点そのものは OCR では埋めないが、登録時に開催条件が揃っていればサーバーが算出し Strength に載せる。出走登録後の編集保存でも同じ照合を再実行するため、OCR で落ちたスキルを追加・並べ替えしても評価用 id を保持できる。辞書に照合できない名称は保存するが、評価対象にはしない。

既存管理の項目分割（開催 / 出走 / 監視 / 着順 / メンバー）は、OCR が1開催分回ったあとにやる。先に情報設計だけしない。分割のとき URL を増やすか、同一管理シェル内の切替にするかは、遷移を抑える話とまとめて決める。`/admin/horses` の当面のフル遷移は捨ててよい。

## 画像の置き場（検討）

1 枚おおよそ 800KB。本戦 18 頭なら 1 開催約 14MB。公開済み開催は残すので、開催を重ねると画像だけが増える。

**D1（いまの無料枠 DB）には画像本体を置かない。**

| 制約 | 無料枠の目安 | 800KB 画像 |
|---|---|---|
| 1 行（BLOB） | 最大 2MB | 1 枚は入る |
| 1 本の DB | 500MB | 画像だけなら三十数開催で上限付近。票・分析ログと取り合う |
| SQL 文の長さ | 100KB | 文に画像を載せる経路は不可 |

読み書き回数の無料枠（1 日の行数）は、開催ごとの十数枚では問題にならない。足りないのは **容量と、画像向きでないこと**。

画像は **R2**（オブジェクトストレージ）が向き。D1 には頭 ID など参照だけ。R2 の無料枠はおおよそ **保存 10GB / 月**（Standard）。800KB なら数千枚、週1・18頭でも数年分は容量上足りる。書き込み・読み取り回数の無料枠もこの規模では余る。egress は R2 側は無料。この催しの規模では **無料枠で保存して問題ない**。

先にやるのは保存できること（R2 バケット、D1 の参照、アップロード）。**メンバーへの表示は今しない。** 管理者向けの表示も後の機能追加。

Workers のリクエストに 800KB を載せることは、このサイズでは問題にならない。

## デプロイ時の OCR 固有の補足

本番リリース全体の確認・復旧手順は [release.md](../operations/release.md) を正とする。ローカルの `npm run deploy` だけでは、**D1 の新マイグレーションと R2 バケットは本番に乗らない**。スクショ保存を本番で使う前に、同手順の中でこの順を確認する:

1. `npx wrangler r2 bucket create oshi-keiba-shots`（初回だけ。既にあれば不要）
2. `npx wrangler d1 migrations apply oshi-keiba --remote`（`0006_horse_uma_runner_shot` など未適用分）

`wrangler.jsonc` の `r2_buckets` にも同じメモがある。

## 範囲（仮）

読むもの（たたき台が要求している入力。遺産の抽出項目と整合）:

- スキル一覧（数、金／緑、無効判定の材料）。**デバフも含む**

### 遺産の穴（忘れない）

skill-emulator はシミュレーション用なので、**緑×（umasim の rarity `minus`）を取得スキルに載せない／umasim 未収録なら落とす**実装がある。ためらい4種は umasim 未収録で rarity 表では **white**。minus とためらいは別物。当アプリの評価点はスキル数が根幹で、ためらいも緑×も材料になり得る。プロンプト・マッチ辞書・フィルタをそのままコピーしない。読取結果にデバフが残ること、金／緑／緑×／ためらいが区別できることを後工程の条件にする。

出さないもの:

- メンバー画面への評価点・読取ログ・スクショの露出（スクショは後ほど）
- 出走の一括貼り付け
- 予選参加者の一括読取
- 着順の自動取得
- アプリ内のライブキャプチャ・スクロール結合・レースシミュレーション
- サーバ経由の Gemini 呼び出し

失敗したらその頭だけ手直しできるようにする。全員分が読めなくても、読めた頭と直置きを混在して setup を終えられることを目標にする。

スキルカタログの生成手順は辞書ファイルを置くときに足す。
