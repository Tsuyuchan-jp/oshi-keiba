# P0-02 詳細設計: 投票・やりなおしの同時実行

> 状態: 実装前の確認用  
> 対象: 同一メンバーによる購入・やりなおしの再送、連打、複数タブ操作  
> 対象外: 結果公開・払戻の同時実行（P0-03で対応）

## この対応で守ること

- 購入が成立したときは、同額だけ残高が減り、馬券が1件だけ作られる。
- やりなおしが成立したときは、未返還の馬券だけが1回だけ返還される。
- 通信が切れた後に同じ送信を再試行しても、購入・返還は重複しない。
- 締切・出走取消のあとに届いた購入は成立しない。
- 同時に届いた操作は、DBが先に確定した1件を正とし、後続操作はその最新状態で判定する。

ここでいう「同じ送信」は、同じ画面に埋め込まれた操作IDを持つ再送です。別タブで改めて購入した場合は別操作として扱います。

## 利用者から見える動き

| 場面 | 結果 | 画面メッセージ |
| --- | --- | --- |
| 購入ボタンを連打した | 最初の1回だけ購入 | 「買いました」 |
| 購入後に通信が切れ、同じ画面で再送した | 以前の購入結果を返す。追加購入しない | 「買いました」 |
| 3,000スペのうち2,000スペを、別タブから同時に2回買おうとした | 先に確定した1件のみ購入。後続は残高不足 | 「残高が足りません」 |
| やりなおしを連打・再送した | 最初の1回だけ全票を返還 | 「やりなおしました（…を戻しました）」 |
| やりなおし後、古い画面から購入を送った | 投票中・残高・対象馬の条件を満たすなら新しい購入として成立。満たさなければ失敗 | 条件に応じた理由を表示 |
| 購入と締切・出走取消が重なった | DBで先に確定した状態を採用。締切後・取消後なら購入しない | 「投票期間外です」または「このウマ娘には投票できません」 |

「やりなおし後の古い購入」は、同じ操作の再送ではなく別の購入意思として扱います。利用者が購入ボタンを押した事実があるため、条件を満たす限り勝手に捨てない、という運用です。

## DBに追加する記録

`member_operations`（名称は実装時に確定）を追加します。

| 列 | 用途 |
| --- | --- |
| `id` | 画面で発行する操作ID。主キー・一意 |
| `event_id` / `user_id` | 誰がどの開催で行った操作か |
| `kind` | `bet`（購入）または `redo`（やりなおし） |
| `request_hash` | 購入額・賭式・買い目など、送信内容の照合値 |
| `result_amount` | 実際に控除または返還した額 |
| `bet_id` | 購入時に作った馬券。やりなおしでは空 |
| `created_at` | 確定日時 |

同じ操作IDを受け取った場合のルールは次のとおりです。

- 記録があり、操作種別・送信内容が一致する: 保存済みの結果を返す。
- 記録があり、送信内容が異なる: 不正または壊れた画面として拒否する。
- 記録がない: 新しい操作として確定処理を行う。

操作IDは認証情報ではありません。ログイン済みの利用者本人・開催ID・送信内容が記録と一致することも確認します。

## 購入の確定手順

画面上の残高表示は案内用です。購入を可否を決めるのは、DB内の最新残高だけです。

1. 操作IDが既に確定済みなら、その結果を返す。
2. DB内で、対象開催が `voting`、対象馬が未取消、利用者が参加済み、かつ残高が購入額以上であることを確認する。
3. 条件を満たすときだけ残高を減らす。
4. 控除成功と対になる馬券・操作履歴を同じDBトランザクションで作る。
5. どれか1つでも失敗すれば、残高控除・馬券・操作履歴のいずれも残さない。

重要なのは、更新件数が0件だったことを成功扱いにしない点です。D1のバッチはトランザクションですが、条件に合う行が0件の `UPDATE` 自体はSQLエラーになりません。そのため実装では、残高控除が成功したことを確認できるSQL構成と結果判定を用います。

## やりなおしの確定手順

1. 同じ操作IDが確定済みなら、保存済みの返還額を返す。
2. DB内で、対象開催がまだ `voting` であることを確認する。
3. その利用者・開催の「未返還票」だけを対象として合計額を求める。
4. 合計額を残高へ加算し、対象票を返還済みにし、各票の `redo` 履歴を作る。
5. 操作履歴に返還額を保存する。
6. 途中で失敗したら全体をロールバックする。対象票が0件なら新規のやりなおしとしては失敗にする。

返還済みへの更新を条件付きにするため、後から届いたやりなおしは対象票を見つけられず、二重返金できません。

## データを守る追加策

- `payouts` には、同じ馬券への同じ種類の返還履歴を重複して作れない一意制約を検討する。これはアプリの不具合が再発した場合の最後の防波堤。
- マイグレーション適用前に、本番DBに既存の重複返還履歴がないことを確認する。重複があれば、制約の追加前に原因と扱いを確認する。
- `member_operations` を参照整合性の対象にする場合は、メンバー削除・開催破棄・デモ初期化で同表も削除する。
- 管理者Undoのスナップショットと復元対象にも同表を含める。含めないと、過去へ戻した後に操作IDだけが残って正常な操作を拒否する可能性がある。

## 管理者・集計への影響

管理画面に新しい操作履歴を常時表示する必要はありません。P0-02では、既存の馬券・払戻・残高の表示を正しく保つことを優先します。

問い合わせ時に確認できるよう、操作履歴はDBに残します。ただし、メンバー削除や開催破棄の既存方針に合わせて関連履歴も削除します。

## 実装前に行う確認

1. ローカルDBで一意制約追加用のSQLを試し、既存データと互換であることを確認する。
2. 本番DBに `payouts` の重複がないことを読み取り専用で確認する。
3. D1の実DBで、条件付き更新・バッチ失敗時のロールバックが想定どおりかを確認する。
4. テスト用DBの `batch()` をトランザクション化し、本番D1と同じ失敗時の挙動を再現する。

## 自動テストの完了条件

- 同一操作IDの購入を2回送っても、馬券は1件・控除は1回。
- 同一操作IDのやりなおしを2回送っても、返還と `redo` 履歴は各馬券につき1回。
- 残高を超える同時購入では、成立した購入の合計額が残高を超えない。
- 購入とやりなおしを同時に実行しても、残高、未返還票、返還履歴の合計が矛盾しない。
- 締切・出走取消と購入が重なったとき、確定後の状態に反する馬券が残らない。
- 意図的に途中のSQLを失敗させても、残高だけ・馬券だけ・操作履歴だけが残らない。

## 実装承認時の対象範囲

- 新規マイグレーション
- 購入・やりなおしのフォームとルート
- `storeRace.ts` の購入・やりなおし処理
- 削除・開催破棄・管理者Undoの関連処理
- テスト用D1と結合テスト

この設計であれば、利用者は通常どおり「買う」「やりなおす」を使うだけで、再送や連打による残高破損を防げます。
